# Code Editor: Input, Language Detection, Issue Markers, Wide Scrollbar

Status: done
Owner: Ilana
Last updated: 2026-10-24

## Goal
- In the Review page code editor, the user can type, paste, or upload a code file.
- The language comes from the language selector, or from the file name when a file is uploaded.
- After a review, each finding is marked on its line in the editor.
- The editor has a wide horizontal scrollbar, so long lines can be scrolled with a finger on mobile.

## Scope
- Frontend only (no `stack:full`) — Revision 1 below adds one backend route (stack:full); no Figma. Branch: `feat/code-editor` (built on `feat/review-tab-placeholder`).
- In scope:
  1. **Typing and pasting.** The Summary tab editor is already editable. Keep native Monaco paste. Pasted and typed code go through the existing `REVIEW_LIMIT.contentMax` check (`pages/ReviewPage.tsx`). Add tests that prove both work.
  2. **Upload.** An "Upload file" button (`lucide-react` `Upload` icon) in the `CodeEditor` header, shown only when the editor is editable. It opens a hidden `<input type="file">`. The `accept` list comes from the extension map (item 3).
     - The file is read in the browser (`File.text()`), never sent anywhere until Run review / Save review.
     - It is rejected with a `sonner` error toast when:
       - its extension is not in the map: "Unsupported file type";
       - it is larger than `REVIEW_LIMIT.contentMax` characters: "File size exceeds limit";
       - it is empty.
       The first two reuse the texts from the Help error table (`lib/help.constants.ts`).
     - On success, the file content replaces the editor content, the editor title shows the file name, and a success toast is shown.
     - Drag and drop of a file onto the editor uses the same handler (see Open Question 2).
  3. **Language detection.** A single map from extension to language, in `lib/review.constants.ts`, for the languages in `languageList`:
     - `.ts`, `.tsx`, `.mts`, `.cts` → TypeScript
     - `.js`, `.jsx`, `.mjs`, `.cjs` → JavaScript
     - `.py` → Python
     - `.go` → Go
     - `.java` → Java

     A pure helper `languageFromFileName(name)` (in `lib/`) returns the language or `null`. On upload the selector switches to the detected language. When no file was uploaded, the selected language is used, as today. Monaco's language id comes from the same map, not from `language.toLowerCase()` alone.
  4. **Issue markers.** `CodeEditor` gets an optional `finding` prop. On mount and whenever the findings change it calls `monaco.editor.setModelMarkers` with one marker per finding:
     - the range is the whole line `lineStart`;
     - severity: critical and high → Error, medium → Warning, low → Info;
     - the hover message is the finding `message` and `detail`.

     It also adds a glyph-margin decoration in the severity color (theme tokens, as in `SeverityDot`), so the line is visible without hovering. Markers are cleared when there is no finding. Findings whose line is past the end of the code are skipped. Only the Summary tab editor gets markers; the Generated tests editor does not.
  5. **Wide horizontal scrollbar.** Word wrap stays off. The editor's horizontal scrollbar gets its own size constant, `editorHorizontalScrollbarSize` in `lib/config.ts`: 16px below `md`, 12px from `md` up (see Open Question 3). Its slider uses the theme scrollbar colors. The app-wide thin scrollbar (`scrollbarSize`, 4px) and the vertical editor scrollbar are unchanged. This applies to both editors (Summary and Generated tests).
  6. All new texts and limits go in `lib/review.constants.ts` (no hard-coded strings in components).
- Out of scope:
  - GitHub file/PR ingestion (next backlog task).
  - Detecting the language from the code content (only selector or file name, as the task says).
  - Adding languages beyond `languageList`.
  - Uploading several files at once, or archives.
  - Any backend or contract change. `language` is already a free string in `NewReview`.

## Assumptions
- `Finding.lineStart` is 1-based and is the only line data the frontend has (no `line_end` in `FindingDto`), so a marker covers one whole line.
- The contract limit `content.maxLength: 100000` is in characters, so the upload size check counts characters after reading, plus a cheap pre-check on `File.size` (bytes ≥ characters) to avoid reading huge files.
- Unit tests mock `@monaco-editor/react` (as the current tests do). Marker logic is therefore tested as a pure helper (`finding` → marker list), and the real Monaco markers are tested in e2e.
- Styling uses Tailwind utilities only, no new CSS files (`.claude/rules/ui-and-styling.md`). If Monaco's glyph class cannot be styled with utilities, the class goes in the existing `globals.css` with theme tokens.

## Open Questions

2. **Drag and drop.** Recommended: **yes**, dropping a file onto the editor works like the Upload button (same checks). Alternative: Upload button only.
3. **Horizontal scrollbar size.** Recommended: **16px below `md` (touch), 12px from `md` up.** Alternative: one size (14px) at every width.
4. **Marker severity mapping.** Recommended: **critical and high → Error (red), medium → Warning (yellow), low → Info (blue)**, matching the dashboard dot colors. Alternative: one marker style for all findings.

**Answers (approved 2026-10-24):**

- 2: yes, drag and drop works like the Upload button.
- 3: 16px below `md`, 12px from `md` up.
- 4: critical and high → Error, medium → Warning, low → Info.

## Risks
- **Monaco markers in jsdom.** Monaco does not run in unit tests. Mitigation: pure helpers for unit tests, real markers checked in e2e.
- **Marker drift after edits.** Monaco moves markers with edited lines, so after heavy edits a marker can sit on the wrong code. Accepted; the next review replaces them.
- **Large uploads freeze the tab.** Mitigation: reject by `File.size` before reading.
- **Wider scrollbar covers the last code line.** Mitigation: Monaco reserves space for the horizontal scrollbar; e2e checks that the last line stays visible.

- **Where things live.** The extension map is `LANGUAGE_META` (language → Monaco id + extensions) in `lib/review.constants.ts`, with `LANGUAGE_BY_EXTENSION`, `UPLOAD_ACCEPT`, `UPLOAD_MAX_BYTE`, `EDITOR_TEXT`, `FINDING_MARKER_OWNER` and `FINDING_GLYPH_CLASS` derived from or next to it. - **Deviation: the upload error texts are in `utils/error-messages.ts`, not `review.constants.ts`.** The architecture rule (and `tests/unit/architecture.test.ts`) keeps every user-facing error text in `utils/error-messages.ts` and allows `toast.error` only in `notification.service.ts`. So there are three new error codes, `file_type`, `file_size` and `file_empty`. `CodeEditor` reports them with `errorReported` and the listener shows them through `notification.service`. They are always shown, since no Settings preference covers them. The toast text is the Help table's message followed by its action, for example "Unsupported file type. Upload a supported source-code file." A unit test checks that the texts start with the Help messages. The empty-file text is new: "The file is empty. Choose a file that contains code."
- **Deviation: the byte pre-check is `File.size > contentMax * 4`, not `> contentMax`.** One UTF-8 character can be up to 4 bytes, so a file with more bytes than `contentMax` can still have no more than `contentMax` characters. Rejecting at `contentMax` bytes would wrongly reject such a file. Only files that are certainly too long are rejected unread. After reading, characters are counted with LF line breaks, the same way the Review page counts them.
- A file with only whitespace counts as empty. When several files are dropped, only the first one is used.
- The `info` severity, which the plan did not list, maps to an Info marker and a blue (`low`) glyph.
- The glyph margin is enabled whenever `finding` is passed. That is the Summary editor, including `/review/new` before Run review, so the gutter does not shift when results arrive. The Generated tests editor has no glyph margin.
- **Styling.** The glyph dots use Tailwind `before:` utilities (`before:size-2 before:rounded-full before:bg-critical|medium|low`) set as Monaco's `glyphMarginClassName`. `globals.css` and the CSS files are unchanged. The slider colors come from Tailwind arbitrary properties on the editor section. They set Monaco's `--vscode-scrollbarSlider-*` variables to `--scrollbar-thumb` and `--scrollbar-thumb-hover`. The app-wide scrollbar rule and the vertical editor scrollbar (`scrollbarSize`) are unchanged.

## Revision 1 (2026-10-24): Run review on an existing review
User feedback after QA PASS: after a file upload, an existing review only offers Save review. The user needs to be able to run a review after an upload and after any change in the editor. This revision is **stack:full**: the backend gets one new route.

**Decisions (user, 2026-10-24):**
- Re-analyze **in place**: the same review id gets new results. Do not create a new review.
- Run review on an existing review is **enabled only when the code or language differs from what was last analyzed** (typing, paste or upload).

**Contract (`.orchestrate/api-contract.yaml` 0.6.0, the source of truth):**
- `POST /api/review/{id}/run`, body `SaveReview`:
  - saves the edit (like PUT), then re-analyzes the same id;
  - the response is 202 with the pending review;
  - 409 if the review is pending, queued or in progress, plus 404, 413 and 422;
  - the results of an older run that finishes late are discarded.
- `GET /api/review/{id}` adds the required fields `analyzedContent` and `analyzedLanguage`, the code and language the current findings belong to.

**Backend scope (`backend/`):**
- `review.service` `run(id, input)` and a run counter (or token) per record, so an older `complete()` cannot overwrite a newer run.
- `analyzedAgo` uses a new `analyzedAt` (set on create and on run). `createdAt` is unchanged, so the Dashboard and History stay as they are.
- `get` returns `analyzedContent` and `analyzedLanguage` from `record.review`.
- Route, validation through the existing `SaveReview` schema, and Vitest + Supertest tests for 202, 404, 409, 413, 422 and the stale-run guard.

**Frontend scope (`frontend/`):**
- The DTO and model get `analyzedContent` and `analyzedLanguage`. Add `review.service` `run` and a `runReview` thunk. Both data sources implement it: the JSON source mirrors the backend and fills the results from its mock analysis, as create does.
- `ReviewPage` on an existing review:
  - shows **Run review** (primary) next to **Save review**;
  - Run review is enabled when the trimmed code or the language differs from `analyzedContent` / `analyzedLanguage`, the code is not empty or too long, the review is not unfinished, and nothing is saving or running.
  - On success: toast `REVIEW_TEXT.started`, clear `findingStale`, and restart the polling until the review finishes. The new findings then mark the code.
- `/review/new` keeps its single Run review button.
- Tests:
  - unit tests for the enable rule (typing, paste, upload, a language change, a revert back to the analyzed code, unfinished statuses);
  - e2e: open a completed review, upload a file, Run review, and the new findings are marked on the uploaded code with the same URL id;
  - e2e: edit, Save, then reload, and Run review is still enabled;
  - the cross-stack test covers `run`.

**Validation (added):**
- All frontend commands, plus `cd backend && npm test` (and typecheck/lint if defined), pass.
- After an upload or edit on a completed review, Run review is enabled. Running it keeps the URL id, goes through pending to completed, and shows the new findings and markers.
- With unchanged code (or code reverted to what was analyzed), Run review is disabled and Save review is still available.
- Running while the review is unfinished gets 409 from the API, and the button is disabled in the UI.
