# Help Tab UI (mock data)

Status: done
Owner: Ilana
Last updated: 2026-10-20

## Goal
- Add a `/help` page ("Help & Support") that explains the application and offers self-service troubleshooting, an error-message reference and a validated Contact Support form, based on the right-hand panels of `frontend/src/assets/code-reviewer-settings.png`. Mock data only.

## Scope
- Frontend only (no `stack:full`); no Figma attached. Branch: `feat/help-tab-ui`.
- In scope:
  1. **Route and nav**: `/help` route; the Sidebar "Help" button becomes a `NavLink`; `MobileNav` gets a Help icon (6 items, see Open Question 4).
  2. **Layout** (as in the image's "How to Create a New Review" screen): title and subtitle, inner left topic list in a card, content panel on the right. Below `lg` the topic list becomes a horizontally scrollable tab row above the panel (same pattern as `SettingsPage`). Topic groups:
     - Getting Started: Create a New Review, View Review Results, Use GitHub Integration, Manage Your Account
     - Features: Main Features
     - Troubleshooting: Common Issues, Error Messages, Contact Support
  3. **Guides** (numbered steps, optional tips box, as in the image): Create a New Review, View Review Results, Use GitHub Integration, Manage Your Account, and Main Features (cards for: structured findings, suggested refactors, generated tests, quality dashboard, review history, GitHub import, settings).
  4. **Common Issues**: six issues (Code review isn't starting, Review is taking too long, Unable to upload code, GitHub repository won't connect, Review results look incorrect, Can't access my account), each a one-line summary. Opening one (accordion) shows: **What happened**, **Possible causes**, **How to fix it** (numbered steps) and **Still stuck?** with a link to the Contact Support topic.
  5. **Error Messages**: a searchable table (filter input matches message, meaning and action) with columns Error message / Meaning / Recommended action, the seven rows from the backlog. Below `md` rows render as stacked cards. Empty state "No matching errors".
  6. **Contact Support**: form with validation, description "Tell us what went wrong and we'll help you resolve it.", fields: Issue type (radio group: Review failed, Code upload problem, GitHub integration, Account or login, Other), Email address, Review ID (optional, hint "Helps support locate the affected review."), Priority (radio group: Low, Normal, High with the given descriptions), Describe the problem (textarea), Submit. Mock submit: after validation, a simulated async call to `submitSupportRequest` resolves, then a success confirmation (inline message with a mock ticket number + `sonner` toast) and the form resets. No real support system yet.
  7. **State**: active topic in local state (URL hash or `?topic=` sync, see Open Question 3). Content as data in `src/mocks/help.ts`; types in `src/types/index.ts`.
- Out of scope: backend/API, real support system or email, article search across the whole Help centre, the Help landing cards and "Popular topics" from the image, thumbs up/down feedback, screenshots/attachments.

## Assumptions
- Reuse existing building blocks: `RadioGroup`, tokens, card classes, `cursor-pointer` on clickable items, thin scrollbars, `rem` units, `lucide-react` icons, `sonner` toasts.
- Validation is plain controlled-form logic (no new dependency): email format, issue type and priority required (defaults: none for issue type, Normal for priority), description required with a minimum length (10 chars) and a max (2000), Review ID optional but, if filled, alphanumeric/dash only. Errors show per field after blur or submit, with `aria-invalid` and `aria-describedby`.
- Per `.rule/security-rules.md`, user input is rendered as text only; nothing is sent anywhere in this iteration.
- The reference image is the "settings/help" concept (`code-reviewer-settings.png`, the backlog's `code-review-settings.png`).
- Terms added to `.doc/glossary.md`: "help topic", "support request".

## Risks
- Large static content may bloat components; keep it in `mocks/help.ts` and keep panels presentational.
- The sixth mobile nav icon may be cramped at 320px; check and shrink the gap if needed.
- A mock submit could be mistaken for real support; the confirmation text says it is a demo until the backend exists.
